# Worktree and Goal

Copied from the MIT-licensed `pi-worktree` and `pi-goal` packages in `narumiruna/pi-extensions` at `012c08dc9c17f7ef4adaf92c6a5fe1d036653c7c`. Original notices are retained in `worktree/LICENSE` and `goal/LICENSE`. The Git safety flows and Goal state machine are reused, with public Pi dialogs replacing the terminal toolkit and a private session-scoped service for Paseo.

## Paseo

Open **Work** beside the composer. Goals and worktrees have their own tabs alongside Jobs and Agents:

- **Work → Worktrees:** repository-grouped inventory of isolated branches, associated workers and changed-file counts. A workspace outside Git is treated as a container: discover child repositories up to two directory levels down, skipping hidden/dependency/build directories and directory symlinks. `.git` files and directories are recognized. Container views include clearly labeled, non-removable main checkouts; a single-repository view keeps the existing additional-worktree list. Session-owned repositories outside the workspace remain included. Discovery is cached for 30 seconds and bounded to 64 roots, 256 scanned directories and 4096 entries; inventory is capped at 100 rows with bounded Git work. Partial failures/limits produce warnings without discarding readable repositories. No repository is initialized and no first-repository mutation target is silently chosen. Open uses an existing native workspace ID when available, otherwise explicitly creates a workspace in the parent project. Per-tree removal retains the candidate's exact confirmation and safeguards; it requires a reaped worker and a clean tree. The current Pi conversation stays in its original cwd. Manual create/prune flows remain available through `/worktree`.
- **Work → Goals:** the parent-session registry holds independent paused goals. Creating an entry saves metadata only, even while the parent is chatting. Explicit Start/Resume requires confirmation and delegates execution to an independent child using the named `coordinator` profile (default `gpt-6.1-sol:high`, provider/account inherited from the owner); Resume preserves the recorded model and instructions; it never starts the parent's singular Goal runtime. Each child runs the existing Goal engine and its own checklist/accounting. Dedicated executions use per-goal automatic-response and no-progress overrides, or the parent's configured defaults when blank. Both default to **unlimited**. Effective limits are shown in confirmation and installed in the child before activation; unrelated child preferences cannot change that confirmed policy. Pause must verify stopped execution before Clear can retain the entry as cleared history. A legacy parent goal is displayed separately and is not migrated.

Worktrees default to **ours**: managed worktrees created by the current Pi session through `/worktree`, its Worktree controls, or isolated subagent launches. **Show all** restores the full repository inventory; **Show ours** switches back. The selection is scoped to the current Pi session. Creation records survive reload and normal commits/branch renames; removed or replaced directories are not attributed to the old creation. A worktree retained after later subagent setup fails still belongs to its creating session. This is display attribution, not permission to remove a tree or resume a worker. Tracking begins with this version: older worktrees without creation identities and arbitrary shell-created worktrees remain available under Show all.

Existing sessions need `/reload` after installation. No Goal is created merely by loading the extension or opening the panel. `/worktree` and the candidate's direct `/goal` commands remain available; terminal menus use public Pi dialogs instead of pi-tui-kit.

## Explicit owned-worktree completion

The owning coordinator session can explicitly record its model judgment with `/worktree complete <task-id> <rationale>` and separately request confirmed cleanup with `/worktree cleanup <task-id>`. The existing session-bound workflow service also exposes `worktree.complete` (`taskId`, `reason`) and `worktree.cleanup` (`taskId`); no native UI changes are required. Completion is auditable and never inferred from a PR, CI, worker exit or clean Git status. Cleanup is limited to verified harness-created ownership and blocks on active users/agents, retained evidence, explicit retention, remaining files (including ignored files), changed branches or reused paths. Missing active-user evidence fails closed. See [completion protocol, safety details and offline tests](../docs/worktree-completion.md).

## Delegated registry protocol

`capabilities.delegatedGoals` advertises the version-1 `delegatedGoals` snapshot (`revision`, `entries`). `capabilities.delegatedGoalExecution` separately requires a session-bound child executor whose live `executionAvailable()` preflight confirms required tools and execution policy; mere executor-object presence is not sufficient. Start/Resume rechecks this after confirmation. Saving paused metadata does not require execution availability. Actions use `goals.create/start/pause/resume/edit/limits/clear/add_task/answer`. Create requires `expectedGoalId:null` and optionally `expectedRegistryRevision`; existing entries require exact `expectedGoalId` and `expectedEntryRevision`, except live `goals.limits` uses `expectedPolicyRevision` so usage-only observations do not stale its editor. Requests share serialization and idempotency guards with the workflow service. Stable task IDs survive child attempts; child/group/attempt identities are checked on every operation. Edits omit `tokenBudget` to retain it, or pass `null` to remove an explicit cap; create omits it for unlimited.

Metadata is separate from parent messages and singular `goal-state`, keyed to the parent session under `$PI_DELEGATED_GOALS_STATE_ROOT` or the XDG state directory. Completed and cleared entries are retained. Cross-process mutations first persist a pending-intent journal; uncertain child delivery or metadata persistence failure blocks affected-entry mutations and new child execution across reload until ownership is reconciled. Unrelated paused metadata can still be created or edited without discarding the pending journal. There is currently no automatic reconciliation API: uncertain delivery requires authoritative manual inspection of the owned child/task binding before an operator can repair the journal; merely refreshing never clears it. The service does not silently retry a failed launch or cancel active children when disposed/cleared. Paused linked edits are metadata-only and never launch, prompt or journal a child mutation. The next explicit confirmed Resume carries the current entry and synchronizes its objective, explicit budget (including cap removal) and checklist into the existing paused child engine before activation. Cached inactive child observations cannot overwrite those edits. Resume rejects missing metadata rather than silently running stale scope.

Trusted dedicated workers opt into `workflows(pi, {delegatedChild:true})`, which installs only their existing Goal engine and the internal structured lifecycle seam, not another parent registry. The option passes a metadata-only restore policy into the existing lifecycle before startup restoration: restored active goals become paused, pending waits/continuations are cancelled, and no active contract or wait timer is installed before explicit authenticated Resume. No prompts are interpreted as slash commands.

Each entry may also contain a bounded version-1 `story`. Timeline events come from registry mutations and real child engine/checklist transitions. Activity records successful explicit `notify_parent` updates, never arbitrary assistant text or inferred tool activity. Legacy goals have no invented earlier history. Event IDs and timestamps survive refresh/reload; authenticated retained completion can recover the child's recorded story.

Goal review metadata is additive and requires the matching bridge pin. `capabilities.goalReview` gates explicit authenticated UI registration via `goals.reference`. Dedicated workers can also use the optional `goal_reference` tool with their child goal/activation/revision and an idempotent request ID. It is inherited only when the parent allows both `goal_reference` and `read`, and profile/retained restrictions retain that narrowing. Its actual file read runs through `ctx.executeTool("read", ...)` before hash registration, so read hooks and permission decisions remain authoritative. The opened file must still match its pre-authorization device/inode/size/mtime/ctime; changing or replacing a file during read authorization cannot register different bytes. Receipts are stored before acknowledgement, survive unrelated task revisions, reject conflicting request IDs, and fence retries after uncertain persistence until authoritative restore. Root/nonmatching sessions, denied read, old runtimes without nested-read support, stale activation/revision and unregistered preview IDs fail closed. A new helper does not widen a restricted or retained worker's tool list. It records at most 16 immutable source/deliverable references on the exact goal, task, child and attempt. Terminal outcomes remain terminal when a review annotation is added. Local paths must be relative to the exact retained native task workspace, with both parent and recorded child read policy enabled. Traversal, symlinks, nonregular files, changed/deleted files and oversized content fail closed. Text is bounded to 32 KiB UTF-8; PNG is bounded to 256 KiB and 16 million pixels. HTTPS links are never fetched by the producer. Preview resolves only a registered ID and freezes file content by SHA-256; it never accepts an arbitrary path, executes markup or launches a host application. Resume makes prior-attempt references historical/nonactionable until explicitly registered for the new attempt. The bridge can export a bounded user-requested JSON snapshot to the clipboard; no automatic repo writes or global archive migration are introduced. `questionnaire` accepts up to eight explicit `attachmentIds` from this worker's `goal_reference` results. The recorder creates immutable, distinct question-bound references with the exact goal/task/child/attempt/worker epoch and generated question ID. Preview also requires the actual question revision and epoch; an attachment cannot be borrowed by another question or opened through the generic reference route. Goal-local IDs stay in the durable goal question and Goals review UI; the owner-human forwarding DTO contains the unchanged questions/options without transferable local file IDs. Pending attachment references are protected during bounded merge; historical eviction is explicit.

Story coverage marks actual record/byte-budget eviction, while absent legacy coverage stays unknown. Per-entry observation health is a transient projection, not a lifecycle transition, checklist update or persisted running claim. Failed observation cannot erase durable metadata or paused parent edits. Engine-owned blocker/wake/deadline diagnostics are projected separately from task statuses and execution ownership. Optional authored questionnaire background and recommendation remain display context: nothing is selected or submitted automatically.

`capabilities.goalPlanning` gates the parent-owned advisory planning surface. `goals.dependencies` accepts explicit same-goal task IDs and `waitsFor`; self, duplicate, foreign and cyclic edges are rejected. It never schedules or changes a task/goal lifecycle. `goals.blocker.add` records a bounded reason, evidence and optional existing task ID; `goals.blocker.clear` addresses the exact durable blocker ID and retains original evidence plus clear time/history. Both use the existing authenticated owner, expected goal/entry revision and request-ID lane, not a new model consent path. Real task removal prunes invalid advisory edges while preserving historical blocker evidence.

These optional fields are accepted by the coordinated bridge schemas; older producers can omit them. Publish producer and bridge pins together: older strict bridge consumers must not receive newly emitted metadata. No change requires a native host SDK update. The footer remains exactly the existing Goal tick/square contract.

Questions reuse the existing `questionnaire` tool and typed worker-interaction format when the parent/profile allow that optional tool. The dedicated worker keeps the actual pending tool promise and durably records its request and answer. `goals.answer` requires the goal/entry revision, question ID/revision, worker epoch, typed answer and idempotent request ID; the private executor rechecks the exact child binding. Closing the panel does not cancel questions. Aborts and worker restoration cancel pending requests rather than replaying them. This question-only service does not intercept Permission Gate approvals, and answering never starts a new child or sends a synthetic chat prompt. Graceful verified Pause cancels pending questionnaire waiters before the final stopped receipt; answered receipts that raced Pause remain answered. The UI uses neutral pending-question wording and never counts these records as top-level human escalations. Coordinator-first structured guidance is owned by the separate [native guidance lane](../subagent/GUIDANCE.md): `notify_parent` acceptance is still a notification receipt, not waiter resolution. The goal questionnaire recorder now preserves its exact local waiter/history while forwarding through the selected owner-human service, and records the real human receipt before resolving. Local answers, aborts and shutdown cancel outstanding forwarding; late replies cannot overwrite a settled answer. Only the top-level existing human questionnaire supplies preference answers; model guidance replies cannot approve them or permissions.

## Existing per-child/terminal Goal engine: model-managed goals and tasks

`update_progress` and `goal_manage` use one authoritative goal record and mutation service. Objectives are concise outcome-only statements (at most 320 characters); implementation and verification steps live in that record's tasks. **Creation authorizes autonomous continuation by default**, with configured limits; `start:false` creates a paused draft. This is the tool contract, not a request to separately assert `user_authorized:true` on creation. Existing goals—including paused goals—must be explicitly cleared or successfully completed before another is created. Creation cannot bypass pending permissions, another workflow, or native dedicated-child ownership. Tool-driven activation binds the current run rather than recursively submitting a prompt.

`goal_manage status` is read-only and returns stable `id`, `activationId`, shared `revision`, tasks and limits. `goal_manage create` is an alias for checklist creation (requires `request_id`, optional `steps` and `start`; optional `token_budget` is an explicit cap). Pause/resume/clear/complete and objective/scope updates require exact `goal_id`, `activation_id`, `expected_revision` and fresh `user_authorized:true`. Automatic Goal turns cannot reset limits, replace a goal or resume themselves. Task-only updates never resume a stopped goal. Omitted token budgets on creation mean unlimited; omitted budgets on updates preserve the current policy.

When the user explicitly asks to complete a **paused** goal whose outcome is already verified, use `goal_manage action:complete` directly—do not resume it or create an active Goal contract merely to complete it. Read status first, then supply the exact identity/revision, fresh authorization and a nonempty verification summary:

```json
{"action":"complete","goal_id":"<id>","activation_id":"<activationId>","expected_revision":5,"user_authorized":true,"summary":"Verified the outcome and every required task with passing tests and inspected results."}
```

Every required task must already be `completed`; missing, contradictory or oversized summaries and stale/foreign controls are rejected. This action accepts paused goals only, not active, blocked or terminal states. It archives the real summary and checklist, preserves usage recorded before pause, clears the current goal and its continuation/wait state, and terminates without starting a model turn or acquiring autonomous execution authority. Dedicated children still cannot mutate `goal_manage` lifecycle state. Active autonomous completion remains `goal_complete` with its existing active-contract/ownership safeguards.

### Goal tool transcript presentation

Pi renders calls as `Goal manage <action>` (no raw arguments). Successful results with an objective render only `Objective: <objective>`, including expanded views. Quotation marks, punctuation and newlines are objective data, not parsed from the control prose. Errors and results without an objective retain their diagnostic text. The full model-facing `content`, existing structured Goal/task data, authorization and termination behavior are unchanged.

Native/Paseo transcript adapters must opt into the same presentation; Pi's `renderCall`/`renderResult` components do not run over RPC. Successful results now add `details.presentation = { version: 1, tool: "goal_manage", action, objective? }` (including pause/clear, where canonical active state may already be gone). `goal/presentation.ts` exports `goalManageTitle(args)` and `normalizeGoalManageDisplay(result, isError)` for adapters. The latter returns `{ text, isError }`, prefers version-1 metadata, supports older `details.goal.objective` results, and falls back to the original text for errors/missing objectives. Never infer success from metadata or use the call's proposed objective as the result.

Consumer followup outside this repository: in the bridge/native tool-call normalization path, recognize `goal_manage`, use the title helper and suppress its generic argument/schema preview; in both live tool-result events and persisted-history replay, preserve `details.presentation` and the actual tool error flag, then use the result helper's text as the entire normal/expanded visible body. Hide generic JSON/details sections for successful objective-bearing results, but retain the original content/details/error/control fields in machine/session storage. Pending calls can use the action from call arguments; successful metadata carries it for result-only replay. No consumer changes or deployment are performed here.

Offline renderer/contract regression: `node --test tests/goal-presentation.mjs`.

### Required tasks

Create atomically, allocating the goal and task IDs in one `goal-state` append:

```json
{"action":"create","objective":"Verified outcome","request_id":"create-1","steps":[{"text":"Implement and verify","status":"pending"}]}
```

Add `"start":false` for a draft. Updates require an explicit non-null goal identity and the current shared revision:

```json
{"action":"update","goal_id":"<id>","expected_revision":4,"request_id":"update-1","steps":[{"id":"<task-id>","text":"Implement and verify","status":"completed"}]}
```

Omitted tasks remain unchanged, including completed tasks. Missing task IDs create new tasks; supplied IDs must belong to this goal. Use `remove_task_ids` only for an explicit user scope change (dedicated children cannot remove parent-owned scope). An empty `steps` array does not clear the checklist. Reuse the identical request ID and payload on retries: durable receipts in the same goal-state record prevent duplicate tasks or a second start, even after reload or clear. Changed payloads with the same request ID are rejected. A stale revision requires status review and a new request ID.

Goal IDs now stay stable across pause/resume and objective changes. A separate activation token fences terminal tools, run ownership, queued prompts and callbacks. `goal_complete`, `goal_wait` and `goal_blocked` require both `goal_id` and `activation_id` from the latest contract. Checklist updates alone never complete a goal; explicit completion still requires verified outcome evidence and no unfinished tasks. UI task additions remain paused/idle-only.

### Migration and compatibility

- Existing goal-linked scoped progress is copied losslessly into the goal record using only its explicit legacy `progressId`/ID association. Existing task IDs, text, statuses and completion are retained; missing legacy IDs receive deterministic IDs. No tasks are associated by matching text or timestamps.
- History/tree navigation invalidates the previous execution lease and restores only the selected branch's explicitly linked goal/tasks. Active goals are paused on navigation until explicit Resume; counters and stable identities are retained. A fresh activation token and monotonically fenced revision reject pre-navigation callbacks. Navigation does not merge tasks across branches or authorize replay.
- Unrelated standalone histories remain readable in history, but are never shown as a current checklist without an owning goal. New standalone writes (including omitted/null `goal_id` on updates) are rejected. Enabling Progress through Nix also includes its required Workflows backend. The progress widget, status and UI snapshots read the canonical goal tasks; legacy scoped writes cannot override a migrated record.
- `revision` is the optimistic task/control fence: task, objective/scope, lifecycle, activation and goal-policy changes advance it. A new request receipt also advances it, even for an empty/no-op task patch. Accounting-only checkpoints (tokens, time, iteration, safety counters and timestamps) persist in the same record without invalidating a revision already supplied to the model. The `Current goal data` context and `goal_manage status` expose this canonical revision before generation. Limit editors separately use `policyRevision` to fence policy/activation changes without being invalidated by task-only or accounting updates.
- Bridge assigned-goal controls must send `expectedActivationId`; non-limit mutations also send `expectedGoalRevision`. `goal.limits` retains `expectedPolicyRevision`. Delegated `goals.limits` uses the entry's new `policyRevision` as `expectedPolicyRevision`, not its frequently changing `revision`. Service/worker epochs and exact child identity checks remain required. Old clients fail closed and need a compatible bridge update.
- Model/tool callers must migrate to the new action/request/revision contract. Dedicated-child controls propagate activation tokens and still require authenticated parent ownership. No deployed session is restarted by this change.

## Observable waiting

`goal_wait` is idempotent while waiting: omit `resume_after_ms` to retain the exact existing deadline, or explicitly supply it to replace the deadline from now. Results contain the current reason, absolute deadline, `changed`, deadline disposition, actual wake semantics, and last recorded wake. Reason text does **not** subscribe to a particular worker. Deadline delivery waits for an idle boundary and has one bounded retry; repeating an unchanged wait does not re-arm exhausted delivery retries.

`goal_manage status` includes current wait, last accepted wake, recorded blocker evidence, last checklist change (not a heartbeat), and a bounded session-owned activity overview with actionable IDs. Session ownership does not establish goal assignment. Provider failures/timeouts are reported as unavailable; pending guidance means queued delivery, not every unanswered request. External wake delivery still depends on harness enablement/admission. Agents should arrange completion/guidance delivery and wait only when no independent parent work remains—not poll merely because workers are active.

Installed-bundle verification: `PI_GOAL_TEST_SOURCE=/nix/store/...-pi-extension-bundle node tests/goal-wait-runtime.mjs <installed-pi-package>` exercises real Pi sessions with an offline scripted provider, without paid calls or changes to user goals.

## Goal boundaries

Both the automatic-response and no-progress limits default to **unlimited**. Nix exposes `programs.pi.extensions.workflows.goal.continuationLimits.automaticTurns` and `.noProgressTurns` (positive integers or `null` for unlimited). Work → Goals exposes both limits on creation/edit; blank inherits the effective configured default and clearing a saved override restores inheritance. No token budget is applied unless the user explicitly supplies one with `/goal --tokens` or `goal_manage.token_budget`; explicit budgets are positive integers capped at one million. Manual settings in `<getAgentDir()>/pi-goal.json` can change the response/no-progress limits, and the confirmation shows the effective values. Trusted-extension managed-run RPC remains disabled by default.

Goal uses the session's selected model, thinking, active tools and existing permission policy. It does not switch models or bypass the idle guard. Starting/updating/resuming requires Pi to be idle in the native controls; Pause can stop an active Goal turn. Continuation uses the copied settled-boundary dispatcher, separate activation tokens, usage accounting, waits and circuit breakers. Automatic continuations are hidden custom messages, not user chat messages. User input interrupts an active wait before model work; it never resumes an explicitly paused goal. Delivered non-Goal custom messages (including admitted completion/guidance), explicit Resume, or an optional safety deadline can also wake a wait. Routine progress does not wake the model. Autonomous finishing requires the copied `goal_complete` evidence contract; explicit user-requested completion of a verified paused goal uses `goal_manage complete` as described above. Ordinary text does not count as completion.

These are not dollar caps. The final request can exceed a token budget and may complete the goal in that same response; otherwise exhaustion stops continuation. Initial/manual tool loops, compaction and independent delegated work are not bounded by the automatic-response count. Parent-session token accounting does not impose a budget on independent child agents. Review the model and active tools before enabling autonomy.

Canonical Goal state is persisted in the session. Reload restores paused/limited state without silently resetting counters. Legacy goals carrying the old implicit 250,000-token default migrate to unlimited; if they were stopped by that cap, they restore paused and require an explicit resume. New explicit budgets are marked and preserved across reloads. A legacy 250,000 cap is treated as the old implicit default because older state did not record whether it was explicitly requested. Cleared and successfully completed goals are retained in session-backed History with distinct outcomes; a clear is never recorded as successful completion. Legacy global state files are left untouched rather than rewritten. The Goals panel uses the neutral History label for both outcomes. Accepted completion state and its matching tool-result evidence are projected separately for the panel.

## Isolated subagent launches

Native Linux subagents accept `worktree: { changes?: "include" | "exclude", base?: string }` on a single launch or each parallel/chain item. Set `cwd` to the source repository (or a directory inside it). Clean checkouts may use `worktree: {}`; the base defaults to the resolved HEAD commit. Any staged, unstaged or untracked changes require an explicit include/exclude choice. Ignored files neither trigger the choice nor get copied.

Include copies staged/unstaged binary patches and untracked files without stashing, committing or modifying the source index/checkout. A dirty include requires HEAD as its base; unresolved merges, unsafe index flags, dirty submodules and oversized snapshots are refused. Exclude uses only the selected commit. Source changes during preparation fail closed. Each requested child gets its own branch and working copy; chain steps do not inherit the previous step's files.

The worker starts in the new working copy, with an explicit instruction to keep edits there. This is Git checkout isolation, not a broader filesystem sandbox; normal permission policy still applies. Resume retains the same working copy. Completion and reap do not merge, remove the worktree or delete its branch. Partial creation failures retain artifacts for inspection. Ownership is persisted and removal refuses attached workers, including idle completed workers until they are reaped. AgentSH-supervised and non-Linux worktree launches are rejected rather than silently using a shared checkout.

## Worktree boundaries

The copied checks protect main/current, dirty/untracked, locked, index-flagged, submodule and unsafe detached worktrees. Ignored files and administrative recovery pointers require their exact preview; inventory and identity are rechecked before Git mutates anything. Branches are never deleted and removal never uses force. Cancel does not roll back an already-applied Git change.

The native backend also checks for open Paseo agents using the selected worktree, including subdirectories and symlink aliases, immediately before forwarding a removal confirmation. It fails closed if the agent inventory is incomplete. This is not an atomic lock against unrelated Git/process activity; keep other processes from modifying a worktree while removing it. Manual workflow Git hooks still run with the host's normal permissions; automated subagent worktree creation disables Git hooks.

Native Git mutation is refused if Pi or Goal becomes active while a preview is open. Native open uses Paseo's workspace API, not session switching or a model prompt. The copied terminal Switch action still uses Pi's public session replacement APIs and its context-preserving flow.

## Transport and tests

Controls bind agent/workspace, Pi session, bridge epoch, service epoch, operation ID, dialog ID and unique request ID. Every confirmation is explicit; no dialog response or mutation is sent automatically on render. Duplicate intent is idempotent; uncertain outcomes require fresh status review and are never automatically retried. Session shutdown invalidates dialogs and cancels owned Git work. Goal status remains readable while Git inventory refreshes independently.

Deterministic SDK tests: `node --test tests/workflows-sdk.mjs`. They exercise real Git and Pi's actual tool/settlement pipeline with fake providers, including destructive-preview races, completion, hard limits, cancellation and reopen. The bridge has compiled client/server/socket tests and an open-agent removal guard test.

The opt-in `PI_WORKFLOWS_LIVE=1 node tests/workflows-live.mjs` creates a disposable local Paseo workspace/Pi session and makes live Luna calls. It verifies native workspace opening, Git guards and branch preservation, then a real Goal-generated/read-back artifact. It cleans up only its owned resources and records evidence under ignored `plans/`. Native device visual/gesture review remains separate.
