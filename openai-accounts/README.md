# Native OpenAI accounts

`/accounts` manages named native OpenAI ChatGPT OAuth grants/API keys and native OpenAI Codex OAuth grants. The two providers have independent named accounts, defaults, session selections, revisions, and runtime refresh state; identical profile names coexist. Account-control requests may specify `providerId` (`openai` or `openai-codex`); omission retains legacy OpenAI behavior. Selection is recorded per Pi session, and restoring a provider default restores that provider's complete built-in authentication/configuration. The native Pi OAuth adapters are used; historical Codex account files are not migrated or deleted automatically. A separately registered custom native provider under `openai` is outside this phase: the extension refuses to install its gate and leaves that provider registration untouched.

Account choice applies to the selected session branch and its inheriting current/future descendants, never its parent or siblings. A child can make its own explicit choice, including **default Pi login**, or **Follow parent account** to clear its override. These are distinct persisted operations: `accountId: null` is explicit default; `inherit: true` with null clears a child override. Branch navigation and resume restore only current-branch account state. Immutable parent identity survives resume without launch environment variables. Private, owner-only per-session routing descriptors follow the immediate parent to the nearest explicit override; broken, unsafe, cyclic, or regressed descriptors block requests. No branch switch changes the global active/default account.

Inherited sessions retain their native provider/model selection instead of registering a `session-follow` virtual provider. At request time, native provider gates resolve the current physical provider with the exact selected role model ID, reject unavailable roles, and preserve all authentication/payload checks. Already-dispatched requests retain their admitted credentials; local switching/clearing is blocked while requests are in flight.

The private store is `<getAgentDir()>/pi-accounts.json`. Credentials are stored with mode `0600`, atomic writes, symlink/path validation, and cross-process locking through vendored `proper-lockfile` 4.1.2 plus its declared runtime dependencies. Other provider sections in an existing store are preserved. Refresh uses the upstream serialized refresh/store path. Failed activation installs the fail-closed auth marker; requests do not fall back to Pi defaults or environment keys.

Credential management is restricted to native TUI mode. API-key entry is visibly labeled and unmasked; use a trusted terminal. Paseo's client receives only the versioned safe account-controls snapshot and can switch existing accounts while a session is idle; it never receives credential values and cannot add, remove, or log in to accounts. For a verified named OAuth binding, the provider-scoped snapshot optionally includes `usage.accountKey`, a hash of the provider ID, account, and user identity (not a credential hash). OpenAI Codex identity keys are Codex-specific and are withheld for custom origins or model/provider authentication-header overrides. Codex never publishes OpenAI's `nativeRegistrationVersion` or `nativeRegistrationKey`. The trusted local Paseo daemon can match that identity against a privately read selected grant to query native quota without switching accounts or refreshing credentials. Default/unverified bindings omit that legacy account proof. Eligible native OpenAI grants instead publish `usage.nativeRegistrationKey`, hashing the native client registration and subject. Default eligibility requires the stored OAuth source, official model/provider origin, and no supported configuration-level authentication overrides; it reads this Pi runtime's agent directory without resolving or refreshing credentials. Paseo can match a same-account Codex companion app registration for read-only plan/app usage after explicit opt-in. This is not independent proof that two logins share an account/workspace, nor a guarantee against arbitrary later request-header hooks. No mismatched login may be silently substituted. Switching makes no model call and does not compact or alter conversation context. Account selection revisions and lifetime epochs reject stale clients; exact request-ID retries replay their original result, while different intent under a reused ID is rejected.

A request-time OpenAI Responses provider-config `streamSimple` wrapper gates ordinary and direct registry dispatch, including physical models routed from `idle-guard`. Codex `openai-codex-responses` dispatch is wrapped at the provider-config `streamSimple` boundary using public ModelRegistry provider registration APIs. Each request synchronizes the provider selection, verifies the effective official ChatGPT origin, binds the selected stored OAuth access token to the runtime Authorization header, and rechecks session, revision, credential identity, and headers immediately before payload dispatch. Stale/deleted Work grants fail closed rather than falling back to the personal root Codex login. Restoring default returns the full prior Codex provider config. Codex default quota identity is read-only and published only when stored OAuth wins, the provider is using OAuth, and no registered/config/model auth override or custom origin can shadow it. It activates and verifies auth immediately before calling the captured native provider; an `onPayload` recheck blocks requests if session, selection revision, activation ownership, or effective auth changed. It uses public ModelRegistry registration/auth methods for the gate; the activation coordinator retains a tested Pi 1.0.0 compatibility path to the private runtime's runtime-API-key setter because no public registry setter exists.

## Validation

The focused Nix checks are `checks.<system>.session-routing`, `checks.<system>.openai-accounts-module`, and `checks.<system>.openai-accounts-runtime`. The runtime check runs owned, synthetic-account standalone Pi processes against the immutable extension bundle, covering native role identity, root/sibling isolation, nearest overrides, explicit default versus clear, historical branch restoration, and cold resume while an existing descendant observes strictly increasing routing revisions. Provider HTTP is forbidden in that fixture.

Live acceptance should use a separate owned agent directory and registered synthetic accounts, never copy user credentials or change user account defaults. Exercise the exact chat's Codex composer control and inspect local binding status (not remote validity or quota), native model identity, descendant inheritance, and unchanged parent/sibling selections. Opening Work/BTW controls must not promote background sessions. Account-control confirmation must never issue a model request.

Enable with `programs.pi.extensions.accounts.enable = true;`. In `/accounts`, choose a provider, then **Credential status and usage link** to inspect the session-bound effective credential and its official settings page. This is local credential status, not quota or billing telemetry; no remote entitlement is queried. API keys link to OpenAI Platform usage settings, ChatGPT grants to ChatGPT usage settings. Unknown/unavailable credentials have no inferred link.

`/usage` has been retired. The legacy `programs.pi.extensions.usage.enable` option and `openai-usage` package selection remain compatible: Nix installs `openai-accounts` as a dependency, and the legacy entrypoint registers no command. Prefer `accounts.enable = true` and remove `usage.enable` from host configuration. Non-Nix resource filters that selected only `openai-usage` must select `openai-accounts` instead. The account-controls service and its `usage` bridge schema remain unchanged.
